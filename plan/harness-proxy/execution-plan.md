## Requirement, scope and compatibility
Top-level package enableHarnesses selects Codex and/or DSH; default remains ["codex"]. Remove the separate mkProject dshMcp input with an actionable migration error if supplied. The existing DSH workspace MCP mapping, protection, directory symlinks, and shared .agents/skills and .codex/agents files remain. DSH native agent format conversion, plugin installation, service deployment, secrets, user/global config and launchd management are excluded. The compatibility plugin remains responsible for consuming the shared agent files; this change does not assert runtime agent compatibility.
Generate proxy backend configuration with actual Nix-fixed executable paths for selected packages that explicitly own a backend or already declare a fixed stdio MCP command. Existing HTTP connections have connection metadata only; never infer a command, re-proxy the gateway URL, or silently move an independently deployed service.

## Grounding and decisions
- package.nix currently restricts harnesses to Codex; project.nix selects Codex only and recursively visits dependencies using their own defaults. Therefore a DSH root cannot currently carry its required dependency MCPs into DSH. Root selections will propagate through each dependency edge, unioned when a package is reached from multiple selected roots. Dependency payload identity remains unchanged; [] means no projection on that root path. A dependency separately selected as a root contributes its own selection. Existing default Codex graphs remain equivalent. (Baseline lib/package.nix, lib/project.nix.)
- config.py resolves one canonical MCP map then renders Codex and optional DSH. Preserve that single resolution and filter by each MCP owner's effective harnesses before editor comparison. Both editors still run to clean previously owned unchanged entries when deselected, preserving existing conflict and snapshot checks. Cache includes the selection mapping. (Baseline runtime/config.py desired_mcp, output_editors, main.)
- DSH compatibility reuses Codex agent files and skills, as already approved in plan/dsh-mcp-output/execution-plan.md. Materialize files for the union of selected harnesses. MCP client registration is harness-specific; no second agent format or registration mechanism is introduced.
- Proxy v2 supports command,args,env plus lazyStart,idleTimeout,options; commands are backend deployment definitions, distinct from HTTP client registrations. (mcp-proxy docs/CONFIGURATION.md at cited revision.) Add optional package proxyBackends mapping for explicit owned backend definitions. Names must also be owned MCP names. Require fixed Nix store command; allow only the bounded v2 fields command,args,env,lazyStart,idleTimeout,options, with options limited to autoReconnect and disabled. Explicit metadata takes priority. For ordinary existing stdio MCP declarations without explicit metadata, export the already known command/args/static env and options.disabled:true. Keep the complete original client declaration in connection metadata; name env_vars as operator-supplied requirements, and record cwd or client-policy fields that this bounded projection does not implement. Inferred fragments are operator-completed drafts, never claimed directly runnable. No guessed env substitution, credentials or client-policy remapping. Producer templates needing operator environment completion export options.disabled:true until the operator supplies those values and enables the backend; a generated browser template must not accidentally start its legacy default profile.

## Changes and ordering
1. package.nix accepts codex/dsh, validates proxyBackends, retains metadata in payload and passthru so command string contexts remain in the closure. Metadata is harness-independent; overrides must not rebuild payload solely for selection.
2. project.nix traverses with root harnesses; selected union supplies skills/agents, MCPs and explicit backends. Manifest gains mcpHarnesses per owned server; retain legacy dshMcp only as derived manifest information, never as user control. New runtime reads mcpHarnesses; old manifests retain prior behavior. Remove project argument dshMcp via migration error rather than silently ignoring it.
3. Runtime filters the once-resolved MCP definitions for each editor; existing state cleanup handles selection removal, equal reuse and conflicts. No change to leaf copying, state schema or atomicity guarantees.
4. Project output exposes mcp-proxy.json ({mcpServers: explicit or disabled inferred stdio backend map}) and mcp-connections.json (owner, complete original client declaration, backend source explicit/stdio/none, manual-completion notes, selected harnesses). These are read-only Nix outputs, not auto-copied into user gateway configuration. README explains manual merging, runtime environment completion, GC retention by installed project, endpoint sharing and no secret values in Nix expressions/store. No mcpProxy/auth/port configuration is generated.
5. Focused existing evaluation/runtime tests and README/examples migrate to root override usage. Preserve old historical records; latest README replaces the now-superseded special-flag instructions. Browser producer registers HTTP and supplies backend metadata in its separate dependent PR.

## Invariants and alternatives
Selecting DSH only must not register its MCPs in Codex; a shared dependency reached by Codex and DSH roots appears once in payload and in both appropriate MCP outputs. Duplicate different payload identities and duplicate export names continue to fail. Unknown harnesses fail. On deselection, unrelated or hand-edited configuration is protected and shared files remain whenever any selected harness needs them. Generated proxy data never includes an inferred upstream pointing at its own frontend URL. Backend path contexts stay retained in package/project closure. Literal env values are supplied by producer/user at evaluation and are never read from the activating process.
Alternative: keep a project-wide boolean; rejected because it cannot express root-level subsets and is the specific user-reported interface problem. Alternative: auto-generate all HTTP proxy upstreams; rejected because ownership/deployment is unknown and may form loops. Small explicit producer metadata is sufficient.
Public selection and proxy-export outputs are requirement-backed; private graph helpers and manifest field layout are internal design. Existing per-file atomicity and non-transactional multi-file behavior remain. Nix absent in this cloud is a validation limit; no evaluation/build success will be claimed.
