## Requirement and scope
Add an optional .dsh/mcp.json projection of the already owned MCP definitions in agent-env-nix. Only this repository changes. Project users opt in with mkProject { dshMcp = true; ...; }. Default false preserves current Codex-only installation. This option adds MCP output only: it does not enable DSH native agents, change package enableHarnesses, duplicate producer definitions, install the plugin, manage a gateway, or change any real user profile/credential.

## Grounding and decisions
- lib/project.nix and lib/mcp.nix at baseline collect unique producer-owned normalized Codex-compatible MCP declarations. runtime/config.py desired_mcp resolves mcpPortEnv at activation. Reuse that resolved source for both outputs, rather than adding per-producer declarations.
- Plugin src/config.ts DEFAULT_FILES and src/mount.ts locateProjectFile select .dsh/mcp.json before .mcp.json, not a merge. A newly generated preferred file must not silently hide fallback configuration. Refuse first creation when project .mcp.json exists; explain that existing configuration needs explicit reconciliation. Do not touch the fallback.
- Plugin src/project-file.ts parseProjectFile/toClientConfig consume mcpServers with type http or stdio; HTTP uses headers; cwd is relative to the configuration directory. Generate an absolute project-root cwd when producer omits cwd; resolve producer relative cwd against project root. Never interpolate cwd. README claims cwd expansion, but pinned source does not do it; source behavior determines compatibility.
- Plugin src/env.ts expansion and src/mount.ts variablesForMount allow only profile env/envAllowlist. Emit variable references for env_vars, env_http_headers and bearer_token_env_var, never read their secret values at activation. Documentation explains plugin allowlist setup; no global settings edits.
- Plugin silently ignores Codex-only fields. Reject any present enabled_tools (including an empty allowlist) and nonempty disabled_tools rather than silently broadening available tools. Codex required and startup timeout fields remain Codex-specific client policy; they are not projected, and DSH profile settings govern startup/failure policy. Document this distinction explicitly. An empty disabled_tools deny list needs no projection. An explicit empty enabled_tools means no tools and must not become unrestricted access. Map tool_timeout_sec to positive safe-integer toolCallTimeoutMs, otherwise fail with field-only diagnostic. enabled=false emits disabled:true.
- Plugin normalizes names. Preserve source server keys verbatim; document that plugin normalizes its mounted namespace and do not add a separate name validator. Literal source strings containing plugin variable syntax cannot be preserved by this plugin (no escaping); reject those in expanded fields, while generated named environment references are intentional.
Sources: https://github.com/lihuabd/dsh-workspace-mcp/tree/4c7996f3306f198179fe500b8d607716ac1d0da8/src and repository baseline files above.

## Implementation
1. lib/project.nix: boolean dshMcp default false, include in manifest; bundle runtime helper changes through existing installation path. No package or producer schema changes.
2. runtime/config.py: add bounded projection from resolved definitions. HTTP maps url/http_headers and named environment headers/bearer; stdio maps command,args,env/env_vars,cwd. Reject ambiguous same header from multiple sources (case insensitive) or env overlap with different values; safe environment variable names only. Preserve explicit static strings, reject unsupported semantics as above. Diagnostics must not print values.
3. Reuse existing ConfigEditor ownership, preflight, generated alternatives, snapshot-CAS and atomic file replacement through small rendering/source/desired hooks. DSH target .dsh/mcp.json, own bookkeeping .agent-env-nix/dsh-mcp-state.json, same state schema, distinct file. JSON parser preserves unrelated top-level keys and unmanaged server values; same-name unequal entries or hand-edited owned entries fail; equal unowned entries reused without claiming. DSH does not inherit Codex configs. Do not assert visibility of unknown plugin global/parent settings; document default plugin files/searchParents:false.
4. Main prepare gathers both output plans before any publication. Main commit checks all source/state snapshots before publishing, then uses existing per-file protection; no cross-file atomicity claim. Retry after interruption accepts only known generated alternatives. Root retention combines both states. Disabling dshMcp or removing installation removes only owned unchanged DSH entries, leaves manual/unrelated/equivalent unowned entries. Empty JSON containers can remain. Refuse corrupt state and linked target files using existing guards.
5. runtime/activate.sh adds DSH state path to safety checks; all operations remain under project lock and existing prepare-before-resource-copy. Cache key includes output choice and projection-relevant resolved definitions, so opting in or changing port cannot leave stale output. DSH JSON uses the same already resolved literal URL as Codex.
6. README: opt-in example, generated format and env allowlist requirements, supported mapping and explicit limitations; no full DSH compatibility promise. Add focused tests and test result record under plan/dsh-mcp-output.

## Invariants, risk and alternatives
Codex remains unchanged when opt-in absent; both outputs derive from one owner and one activation snapshot; no secret expansion, silent conflict overwrite, fallback hiding, or whole-directory deletion. Representative counterexamples are edited managed values, same-name unowned conflict, existing fallback, unsupported filtering, and interruption between outputs. The preceding fail-before-publication and generated-alternative policies handle these without a new general framework.
Alternative: output separate producer-native DSH declarations. Rejected because it duplicates ownership and settings. Alternative: overwrite the complete DSH file. Rejected because unrelated user entries must survive.
Existing snapshot checks are not OS-level cross-process CAS and multi-output writes are not one transaction; preserve these documented existing limits rather than claiming stronger guarantees. No critical unknown source assumption remains; actual Nix execution availability is a verification constraint, not assumed success.
